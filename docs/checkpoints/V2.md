# AutoVPN V2: continuous catalogue maintenance

Date: 2026-10-04. Base V1: `571905cb2dc85507c0ac8182de3a43477a1a47e2`.
Checkpoint V2 / assembly version 0.1.2 is a bounded development increment, not version 1.0 and not a VPN release.

## Implemented

`CatalogueMaintenance` now owns a long-lived unelevated five-second maintenance loop independently of source refresh. Pulses coalesce; up to two candidate pairs run at once and a pulse admits at most eight nodes, starting no new batch after its 20-second scheduling budget. Each pair contains two sequential HTTPS requests with individual five-second deadlines and a separate 20-second attempt limit. Process cleanup retains its worker slot until completed. Essential shutdown waits for owned work instead of treating cancellation as completed cleanup.

The reviewed Cloudflare and Google HTTPS-204 targets are combined atomically by `TwoTargetProbeTransport`. A single success never publishes health. Both observations require their own matching target/context/digest/worker proof and authenticated empty-204 response from the existing transport. A mixed success/failure is inconclusive with backoff, not Healthy and not a fabricated global network outage. A target-set identity travels with the durable assessment. The production working-list and pre-connect path require that identity. Existing one-target V1 assessments remain stored but must be revalidated, not silently upgraded.

Old successful assessments become due after 25 minutes, ahead of the existing 30-minute eligibility age. Attempt timestamps and retry-after persist in SQLite and reconstruct queue ordering across coordinator recreation/restart. The oldest due work progresses; one active-node priority slot does not consume the entire batch. This does not guarantee all 10,000 nodes can be kept fresh under a two-worker or daily budget limit; unmet work stays pending/stale honestly.

Foreground verification takes the next scheduling turn and uses the same pair/authority/budget. Automatic checks can be paused/resumed in the Servers view. Revoking public-network consent persists first, cancels owned checks/connect/download work, invalidates the refresh fence and keeps the saved catalogue. The existing interface now displays real maintenance phase/counts and only two-target-verified nodes in the working view, with bounded visible rows. Source download completion no longer runs the old short one-target probe tail.

Daily health-payload allowance uses an exact locked reservation of two 8 KiB payload allowances before I/O and persists the reservation. Cancellation/crash does not refund it; a new UTC day permits new work. This is conservative payload/work accounting, NOT measurement or a strict bound of all IP/TLS/DNS/core-setup traffic. Broad source download accounting, metered-network behavior and reserved active-tunnel capacity remain separate open work.

Latency is the midpoint/median of the two measured HTTPS exchanges, not ICMP ping, a historical performance distribution, bandwidth or active traffic. Target configuration changes require new two-target verification. No global TLS trust, certificate-verification policy or protocol implementation was relaxed.

## Tests and evidence

`AstraV2MaintenanceTests` and `AstraV2ConsentTests` add 22 cases covering target validation, atomic publication, mismatched second-target proof, mixed outcomes, no-consent behavior, revocation between targets, pause/cancellation cleanup, bounded concurrency, restarts, freshness, V1 assessment revalidation, durable SQLite metadata and budget contention. These are controlled transport-contract tests, not an actual two-target public-node measurement or packet capture.

The existing official-core protocol and HTTPS suites run separately on Linux and Windows. At the pre-delivery UI commit `f31a3d8a8f1b702fd6df4d9c4e05597fc41868a2`, run `37208299396` passed the normal/native matrix, the five repeated Windows six-protocol suites and WPF smoke. Final delivery evidence identifies its exact later source commit and retains raw TRX rather than inferring results from a workflow title.

An earlier V2 Windows native run `37208118158` failed one existing Shadowsocks positive with TLS_REJECTED. It is retained; its cause is unresolved. A later pass does not retroactively fix or diagnose it. The preliminary repeat-only workflow `37207148984` used wrong variable names and failed before handshakes: that was an authoring error, not an application failure. It is removed from the delivery; the permanent V2 workflow provisions the correct R5 variables. No retries rewrite a failing test as a success.

## Not implemented or not verified here

Installed SCM/TUN/WFP, privileged authenticated handoff, actual network protection/recovery, DNS/IPv6 packet isolation, a Windows 11 installer/upgrade/uninstall/reboot/sleep matrix and long-run soak remain OPEN/NOT_RUN. This code still refuses real TUN in the production broker. No public subscription node was contacted by this checkpoint's test suite. The WPF smoke uses an unconsented profile and verifies navigation/settings reopen only, not an installed connected session or complete UI accessibility.

The broker's standalone legacy admission APIs are not globally converted to the new target-set contract; the actual desktop-maintenance/pre-connect boundary is. A future privileged runtime handoff must enforce equivalent evidence independently. Full source-family discovery, current source provenance, exit/country policy, all transport mappings, fallback networking and all audit acceptance gates remain binding.
